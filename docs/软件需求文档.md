## 1. 文档说明

### 1.1 编写目的

本文档定义「个人财务分析」产品的目标、范围、功能需求、接口需求、界面与交互要求、非功能需求及验收标准，作为产品评审、研发排期、测试验收的统一依据。

### 1.2 读者

产品、设计、前端、后端、测试。

### 1.3 术语

| 术语 | 定义 |
| --- | --- |
| 总资产 | 用户当前持有的全部资产金额合计，单位人民币元 |
| 总负债 | 用户当前全部负债金额合计，单位人民币元 |
| 净资产 | 总资产 − 总负债 |
| 财务分析 | 一份以 HTML 呈现的分析报告，通常由 AI 生成并经开放接口上传 |
| 分析日期 | 该份报告对应的分析基准日，列表必须醒目展示 |
| 开放接口 | 供 AI / 外部系统调用的 HTTP API，用于上传 HTML 分析报告 |

### 1.4 核心需求（V1 必须交付）

1. **页面美观大方**，同时适配电脑屏幕与手机屏幕。
2. **首页重点展示两块内容**：
   1. **总资产、总负债、净资产**
   2. **财务分析列表**：每条标注清楚分析日期；点击后打开对应 HTML 页面；支持 AI 通过开放接口上传 HTML。

## 2. 产品概述

### 2.1 一句话描述

一个面向个人的财务总览与分析阅读工具：打开就能看到家底（资产 / 负债 / 净资产），并能按日期浏览 AI 生成的 HTML 财务分析报告。

### 2.2 要解决的问题

个人财务信息通常散落在银行、券商、记账软件和聊天记录里。用户需要一个干净的入口：

- 一眼看清「我现在有多少、欠多少、净剩多少」
- 把每次深度分析沉淀成可回看的报告，而不是一次性对话
- 让 AI 能把分析成果直接写入产品，而不是手工复制粘贴

### 2.3 目标用户

| 角色 | 说明 | 典型诉求 |
| --- | --- | --- |
| 个人使用者 | 关心家庭或个人资产负债与趋势的人 | 打开即看总览，点开报告细读 |
| AI / 自动化 | 通过开放接口写入分析报告 | 一次调用即可上传带日期的 HTML |

V1 按**单用户个人使用**设计，不做多账户协作、不做对外社交。

### 2.4 成功标准

- 首页 3 秒内完成首屏关键信息展示（缓存命中或本地数据场景）。
- 用户在手机和电脑上都能完整完成：看总览 → 扫列表 → 打开某日分析。
- AI 调用开放接口后，新报告立即出现在列表顶部，分析日期清晰可读。
- 报告页在手机上可流畅滚动阅读，不出现横向撑破、字号过小、按钮点不准。

## 3. 范围

### 3.1 V1 范围内

- 响应式首页（总览卡片 + 分析列表）
- 资产 / 负债明细维护，并据此汇总总资产、总负债、净资产
- 财务分析列表、按分析日期展示与排序
- HTML 分析详情页（只读阅读）
- 开放接口：上传 HTML 分析报告
- 基础安全：接口鉴权、HTML 安全渲染
- 空状态、加载态、失败态

### 3.2 V1 范围外（明确不做）

- 银行 / 券商账户自动同步
- 复杂复式记账、发票识别、预算执行闭环
- 多用户、家庭成员权限、分享到社交平台
- 原生 iOS / Android App（V1 为响应式 Web）
- 报告在线富文本编辑器（报告由外部 AI 生成后上传）
- 投资组合回测、税务筹划等专业投顾能力

### 3.3 关键假设

1. 金额默认币种为 **CNY**，V1 不做多币种折算。
2. 「分析日期」由上传方指定；未指定时取上传当日（服务器时区：`Asia/Shanghai`）。
3. 一份分析对应一份完整 HTML，产品只负责存储、列表与安全展示，不解析报告内部结构。
4. V1 为个人私有数据，开放接口使用密钥鉴权，不对外公开匿名写入。

## 4. 用户场景

### 场景 A：下班打开看家底

用户用手机打开首页，首先看到总资产、总负债、净资产三个数字，确认本月还房贷后净资产是否仍为正。

### 场景 B：回顾某次分析

用户在电脑端打开列表，看到「2026-09-01 月度财务分析」，点进去阅读 HTML 报告中的资产结构、风险提示和建议。

### 场景 C：AI 自动归档

用户在对话中让 AI 完成本月分析。AI 调用开放接口上传 HTML，并带上分析日期 `2026-09-10`。用户刷新首页，列表顶部出现该条，日期标注清楚。

### 场景 D：首次使用

新用户尚未录入资产、也没有报告。首页仍保持美观布局：总览显示 0 或引导录入，列表示空状态，并提示可通过手动维护资产或让 AI 上传第一份分析。

## 6. 功能需求

### 6.1 首页 — 财务总览

**优先级：P0**

#### 6.1.1 展示内容

首页顶部固定为财务总览区，必须同时展示以下三个指标：

| 指标 | 计算规则 | 展示要求 |
| --- | --- | --- |
| 总资产 | 全部资产明细金额之和 | 主数字 + 千分位，保留 2 位小数 |
| 总负债 | 全部负债明细金额之和 | 主数字 + 千分位，保留 2 位小数 |
| 净资产 | 总资产 − 总负债 | 主数字强调展示；为负时使用警示色 |

补充信息（不抢主数字，但建议有）：

- 数据更新时间（最近一次资产/负债变更时间）
- 净资产相对上一次记录的变化（有历史快照时显示；无历史则不显示，禁止伪造 0%）

#### 6.1.2 视觉层级

- 净资产是首页第一视觉焦点，字号与字重高于总资产、总负债。
- 总资产、总负债并列作为净资产的构成说明，电脑端同一行三列，手机端净资产单独占一行，资产/负债在下一行两列。
- 三个数字必须在首屏可见，不得被列表挤出第一屏。

#### 6.1.3 交互

- 点击总览区（或「管理明细」入口）进入资产管理页。
- 总览区加载中显示骨架屏，禁止先闪 0 再跳变到真实值（除非真实值就是 0）。
- 数据获取失败时，保留卡片结构，展示可重试错误态，不影响下方列表独立加载。

#### 6.1.4 数据来源

总览数字必须来自用户维护的资产/负债明细汇总，不允许写死示例数字给真实用户看。

V1 资产/负债分类建议：

**资产**

- 现金及存款
- 投资（基金、股票、理财等）
- 固定资产（房产等，按当前估值）
- 其他资产

**负债**

- 房贷
- 车贷 / 消费贷
- 信用卡及应付
- 其他负债

每条明细字段：名称、分类、金额、备注（可选）、更新时间。

### 6.2 首页 — 财务分析列表

**优先级：P0**

#### 6.2.1 列表内容

每一条分析至少展示：

| 字段 | 是否必显 | 说明 |
| --- | --- | --- |
| 分析日期 | 必显，且为最醒目标签 | 格式 `YYYY年M月D日`，例如 `2026年9月10日`；同一视觉位置、同一字号，用户扫一眼就能对齐比较 |
| 标题 | 必显 | 如「2026年9月月度财务分析」 |
| 摘要 | 建议显 | 上传时可带；没有则不占位留白过大 |
| 来源 | 建议显 | `AI 上传` / `手动上传` |
| 上传时间 | 次要信息 | 与分析日期区分：分析日期是报告说的「哪一天的家底」，上传时间是「何时写入系统」 |

列表按**分析日期倒序**，同一分析日期再按上传时间倒序。

#### 6.2.2 分析日期标注规则

- 分析日期是列表项的主标签，不能只出现在标题文本里。
- 建议左侧或上方使用独立日期徽章 / 日期列，避免和标题混排导致漏看。
- 若分析日期是当天，可附加「今天」；若是本月可附加「本月」，但**不能替代完整日期**。
- 跨年列表必须显示年份，禁止只显示「9月10日」。

#### 6.2.3 交互

- 点击整行 item（不限于标题文字）进入该分析的 HTML 详情页。
- 电脑端 hover 有轻微反馈；手机端点击热区高度不小于 48px。
- 列表支持下拉刷新（手机）与分页或「加载更多」。V1 每页 20 条。
- 空状态文案明确两件事：还没有分析；可以通过 AI 开放接口上传 HTML。
- 删除：V1 提供删除入口（列表滑动或详情页），删除需二次确认。不做回收站。

#### 6.2.4 列表与总览的关系

- 两块内容同属首页，但视觉分区明确：上总览、下列表。
- 列表区域标题使用「财务分析」，右侧可显示条数。
- 列表加载失败不得把总览一起卸掉。

### 6.3 分析详情 — HTML 阅读页

**优先级：P0**

#### 6.3.1 页面结构

- 顶栏：返回首页、分析日期、标题。
- 主体：完整渲染该条分析的 HTML。
- 顶栏在手机端保持简洁，返回按钮易于点按。

#### 6.3.2 HTML 展示要求

- 打开的是**该条分析对应的 HTML 页面**，而不是把源码当文本展示。
- 报告应在独立渲染容器中展示（推荐沙箱 iframe），避免报告内 CSS/JS 污染壳应用。
- 电脑端阅读区最大宽度约 880–960px 居中；手机端左右留出安全边距，图片与表格自适应宽度。
- 支持报告内部基础交互（折叠、锚点、表格横向滚动），但禁止报告跳出到未授权外链而不提示。
- 若 HTML 为空或损坏，展示「报告无法打开」和返回列表。

#### 6.3.3 安全约束

上传的 HTML 视为不可信内容：

- 渲染时使用沙箱（至少限制 `allow-scripts` 以外的敏感能力；若报告确需有限脚本，只开放最小权限）。
- 服务端保存原文，但展示前做基础消毒：剥离 `<script>` 访问父页面、`javascript:` 链接等危险能力的策略需在技术方案中明确。
- 不在 HTML 中注入用户未授权的统计脚本。

### 6.4 开放接口 — AI 上传 HTML

**优先级：P0**

#### 6.4.1 能力说明

AI 或外部系统可通过开放接口上传一份 HTML 财务分析。上传成功后：

1. 写入分析库
2. 首页列表按分析日期可见
3. 点击 item 即可打开该 HTML

#### 6.4.2 接口定义

`POST /api/v1/analyses`

**鉴权**

- Header：`Authorization: Bearer <API_KEY>`
- API Key 由系统为该用户签发，可重置
- 缺少、错误、过期的 Key 一律返回 `401`

**请求体（JSON）**

```json
{
  "title": "2026年9月月度财务分析",
  "analysisDate": "2026-09-10",
  "summary": "净资产较上月增加 1.2 万元，负债结构稳定。",
  "html": "<!DOCTYPE html><html>...</html>",
  "source": "ai"
}
```

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| title | string | 是 | 1–80 字，去除首尾空白 |
| analysisDate | string | 否 | `YYYY-MM-DD`；缺省为服务器当天 |
| summary | string | 否 | 最长 200 字 |
| html | string | 是 | 完整 HTML 文档或 HTML 片段；大小上限 2MB |
| source | string | 否 | `ai`（默认）或 `manual` |

**成功响应 `201`**

```json
{
  "id": "anl_20260910_001",
  "title": "2026年9月月度财务分析",
  "analysisDate": "2026-09-10",
  "summary": "净资产较上月增加 1.2 万元，负债结构稳定。",
  "source": "ai",
  "createdAt": "2026-09-10T16:08:00+08:00",
  "detailUrl": "/analyses/anl_20260910_001"
}
```

**错误码**

| HTTP | 场景 |
| --- | --- |
| 400 | 缺标题、缺 html、日期格式错误、超出大小 |
| 401 | 鉴权失败 |
| 413 | 超过 2MB |
| 429 | 超出频率限制（建议 60 次/小时/Key） |
| 500 | 服务端异常 |

#### 6.4.3 配套接口（V1 建议同时具备，便于联调）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/analyses` | 分析列表，支持按日期筛选、分页 |
| GET | `/api/v1/analyses/:id` | 单条元数据 + HTML |
| DELETE | `/api/v1/analyses/:id` | 删除分析 |
| GET | `/api/v1/summary` | 总资产、总负债、净资产 |

以上接口与页面使用同一套数据，避免「页面一套、AI 一套」。

#### 6.4.4 给 AI 的使用约定

- 调用方必须传入可读标题，并尽量传入 `analysisDate`，不要依赖默认当天。
- `html` 必须是可独立打开的内容：自带基础样式，不依赖外部未授权脚本。
- 同一 `analysisDate` 允许存在多份报告（例如月报与专题），列表用标题区分，不覆盖历史。
- 若未来需要「覆盖某日最新一版」，另开版本字段；V1 不做静默覆盖。

### 6.5 资产管理（总览数字的支撑能力）

**优先级：P0（没有它，首页三个数字无法成立）**

- 用户可新增、编辑、删除资产与负债明细。
- 保存后首页总览立即按新汇总刷新。
- 金额只允许数字，最小单位 0.01 元；不允许负数（负债用负债列表表达，不在资产里记负数）。
- 手机端使用底部表单 / 全屏编辑，电脑端可用右侧抽屉或独立页。

---

### 6.6 通用状态

所有 P0 页面必须具备：

| 状态 | 要求 |
| --- | --- |
| 加载 | 骨架屏，布局稳定，不抖动 |
| 空 | 说明「为什么空」和「下一步做什么」 |
| 失败 | 人类可读原因 + 重试 |
| 成功 | 写入类操作有轻量反馈，不打断阅读 |

## 7. 界面与交互需求

### 7.1 设计原则

- **大方、克制、可信**：财务产品以清晰和信任为先，避免花哨渐变堆砌、避免表情包化图标。
- **数字优先**：金额是主角，装饰让路。
- **一张首页讲完两件事**：家底，以及历次分析。
- **双手都能用**：电脑上看宽屏总览，手机上单手可点、可回。

### 7.2 响应式断点

| 名称 | 宽度 | 布局 |
| --- | --- | --- |
| 手机 | `< 768px` | 单栏；顶栏精简；净资产单独一行；列表全宽卡片 |
| 平板 | `768–1023px` | 总览三卡同一行；列表仍全宽 |
| 电脑 | `≥ 1024px` | 内容区居中，最大宽度 1120px；总览三卡同一行；列表可左侧日期 + 右侧标题摘要 |

额外要求：

- 适配常见手机安全区（刘海、底部横条），主按钮不被系统手势遮挡。
- 横屏手机仍可用：总览可改为三列压缩，列表不错位。
- 不出现仅电脑能用、手机只能缩放网页的情况。
- 触控目标 ≥ 44×44px，正文 ≥ 15px，金额数字在手机上仍需一眼可读。

### 7.4 视觉规范（V1 约束，供设计落地）

- 风格：浅色为主，留白充足，卡片圆角克制（8–12px）。
- 色彩：中性背景 + 一个主色；净资产为正用稳定色，为负用警示色；不要三张卡片三种高饱和底色。
- 字体：系统字体栈即可，数字建议等宽或特征清晰的数字字体，避免金额识别困难。
- 金额统一：`¥` + 千分位 + 两位小数，全站一致。
- 动效：只用于状态切换与页面转场，时长短、不弹跳。

### 7.5 无障碍与可用性

- 三个总览数字需有文字标签，不能只靠颜色区分正负。
- 列表项使用可访问名称，包含标题与分析日期。
- 键盘可进入详情（电脑端）。
- 对比度满足日常阅读，浅灰字不能看不清。

## 9. 非功能需求

### 9.1 体验

- 首页首屏关键内容在常规 4G 下 3 秒内可见。
- 列表滚动流畅，打开 HTML 报告的等待需有明确加载态。
- 手机与电脑使用同一套产品，不维护两套交互语义。

### 9.2 兼容

- 电脑：最新两个稳定版本的 Chrome、Safari、Edge。
- 手机：iOS Safari、Android Chrome 近两个大版本。
- 不要求支持 IE。

### 9.3 安全与隐私

- 资产、负债、分析报告均为个人敏感数据，默认仅本人可见。
- 开放接口必须鉴权，Key 不以明文写进前端仓库。
- HTML 按不可信内容隔离渲染。
- V1 若先做本地/单机部署，仍需避免报告 HTML 突破应用壳。

### 9.4 可靠性

- 上传接口需幂等建议：可选 `Idempotency-Key`，防止 AI 重试导致完全重复的多条（V1 可为建议项）。
- 删除不可恢复，文案必须说清楚。

### 9.5 可维护

- 前端页面与开放接口共用数据模型。
- 分析 HTML 与元数据分离存储，列表接口默认不返回完整 HTML。

## 10. 验收标准

### 10.1 首页总览

- [ ] 首页首屏同时看到总资产、总负债、净资产
- [ ] 净资产 = 总资产 − 总负债，抽查至少 3 组数据（含负债大于资产）
- [ ] 净资产为负时颜色与文案可区分，且不只靠颜色
- [ ] 电脑为三列（或等价并列），手机净资产优先、资产与负债次之
- [ ] 修改一条资产或负债后返回首页，三个数字正确变化

### 10.2 财务分析列表

- [ ] 每条都有独立、清晰的分析日期，格式含年月日
- [ ] 点击列表任意热区打开对应 HTML 页面，而不是源码
- [ ] 列表按分析日期倒序
- [ ] 空列表有引导，不出现错乱空白
- [ ] 分析日期与上传时间如同时展示，含义不会被混淆

### 10.3 开放接口

- [ ] 使用正确 API Key 上传 HTML 后返回 201，列表立即可见该条
- [ ] 请求中的 `analysisDate` 与列表展示日期一致
- [ ] 未传 `analysisDate` 时使用当天日期
- [ ] 错误 Key 返回 401，列表不被写入
- [ ] 超大 HTML 被拒绝，系统保持稳定
- [ ] 打开新上传条目，所见即所传 HTML 的渲染结果

### 10.4 美观与适配

- [ ] 设计走查：页面整洁大方，层级清楚，不拥挤、不花哨
- [ ] iPhone 逻辑宽度 390、Android 360、电脑 1440 三套宽度下布局不破版
- [ ] 手机安全区、横屏、超长标题、超长金额（千万级）均不溢出
- [ ] 总览与列表在手机上无需双指缩放即可阅读和点击
